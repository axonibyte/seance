# The replication wire

What `seance repl` actually runs, why each flag is there, and the evidence for
each claim. Every observation below was made in a reaper `freebsd-15.1` session
(FreeBSD 15.1-RELEASE-p2, OpenZFS `zfs-2.4.2-1`) with the commands as written;
nothing here is asserted from memory. Where a claim is not observed, it says so.

---

## 1. The names

    <dataset>@seance-<homenodekey>-<YYYYmmddTHHMMSSZ>

The snapshot name is the wire protocol (handoff §2.1). `<homenodekey>` is the
`[a-z0-9]+` config key of the node the guest is at home on (D-4); the timestamp
is UTC, sixteen characters, and the format sorts. seance writes only names it
would itself parse, and it parses from the right so that a node name containing
a dash survives the round trip.

A name that does not parse is **foreign: ignored, never an error, and never
destroyed.** So is a name that parses but belongs to another node's lineage.
Everything below that walks a snapshot list obeys that rule.

## 2. The tick, per guest, per peer

    1. zfs snapshot -r <root>@seance-<home>-<ts>     once per guest per tick
    2. finish any interrupted receive on the peer, from its resume token
    3. per dataset: send the increment, or the whole thing
    4. hold the shadow-mount law on every replica dataset
    5. prune both ends by the same ladder, protecting the base
    6. write the lag record

Step 1 happens once, before any peer is contacted, so that every peer receives
the same instant. `-r` is what makes it one instant: a guest whose root and
whose child were snapshotted a second apart has a replica that is not a point
in time.

## 3. The commands, verbatim

    # probe the peer (one round trip: datasets, tokens, snapshots)
    ssh <peer> 'zfs list -H -o name -t filesystem,volume -r <replica-root>
                zfs get -H -o value receive_resume_token <each>
                zfs list -H -o name -t snapshot -r <replica-root>'

    # resume, when the peer holds a token
    zfs send -t <token> | ssh <peer> \
        zfs recv -s -u -x mountpoint -x canmount <replica-dataset>

    # incremental
    zfs send -p -I @seance-<home>-<base> <dataset>@seance-<home>-<new> |
        ssh <peer> zfs recv -s -u -x mountpoint -x canmount <replica-dataset>

    # first send of a dataset, when the two ends have nothing in common
    zfs send -p <dataset>@seance-<home>-<new> |
        ssh <peer> zfs recv -s -u -x mountpoint -x canmount <replica-dataset>

    # the standby parents, asserted every tick
    ssh <peer> 'zfs create -o canmount=noauto -o mountpoint=none <standby>'
    ssh <peer> 'zfs set mountpoint=none <standby>'      # only if it drifted
    ssh <peer> 'zfs set canmount=noauto <standby>'      # only if it drifted

    # the law, on every replica dataset, every tick
    ssh <peer> 'zfs inherit mountpoint <rds>'   # only if local or received
    ssh <peer> 'zfs set canmount=noauto <rds>'  # only if it is not already

    # pruning, one named snapshot at a time, both ends
    zfs destroy <dataset>@seance-<home>-<ts>
    ssh <peer> 'zfs destroy <replica-dataset>@seance-<home>-<ts>'

Every one of these is bounded in time by `timeout(1)`: control commands get
60 s, a stream gets the guest's cadence or 1800 s, whichever is larger. A
stream that outlives its budget is killed and the next tick resumes it from the
peer's token — which is the whole point of `-s`.

## 4. Why `-p` and not `-R`

`-R` sends a whole tree as one replication stream. Two problems, and the second
is disqualifying:

1. `-R` implies `-p`, so the properties come anyway — that part is not the
   objection.
2. An incremental replication stream is only receivable in practice with `-F`,
   and `zfs-receive(8)` says of `-F`: *"If receiving an incremental replication
   stream (for example, one generated by zfs send -R -[iI]), destroy snapshots
   and file systems that do not exist on the sending side."* seance has no such
   authority over a peer's pool. A foreign tool's snapshot on a replica is not
   seance's to destroy, and neither is a dataset seance did not create.

So the tree is walked one dataset at a time — the adapter already promises the
list, root first — and each dataset carries its own properties and its own
resume token. The costs of that choice are stated in §8.

## 5. Why `-p` is load-bearing, and why `-x mountpoint` is

`zfs send -p` puts the dataset's **locally set** properties into the stream. A
CBSD guest's dataset carries a local mountpoint, set at creation
(`sudoexec/mkdatadir:14-23`). So the mountpoint travels — and a receive without
`-x mountpoint` plants it on the replica. Observed, on a source whose
mountpoint is local:

    # zfs send -p .../web01@... | zfs recv -s -u -x canmount .../standby/alpha/nox
    .../standby/alpha/nox   mountpoint   /u4b/guests/web01   received
    .../standby/alpha/nox   canmount     on                  default

That is a second dataset claiming the live guest's mountpoint: the August
defect, reproduced in one command. With the flag:

    # zfs send -p .../web01@... | zfs recv -s -u -x mountpoint -x canmount .../standby/alpha/web01
    .../standby/alpha/web01 mountpoint   none    inherited from .../standby/alpha
    .../standby/alpha/web01 canmount     on      default

**Note the second line.** `canmount` is not an inheritable property: a received
dataset takes the default `on` whatever its parent says, and `-x canmount` only
keeps the *source's* value out. `mountpoint=none` is what actually prevents the
mount, but a replica that could mount the moment somebody set a mountpoint on
it is one edit away from the defect. So seance **sets `canmount=noauto`
explicitly** on every replica dataset, every tick, and repairs it when it has
drifted. The receive flag alone is not the enforcement; this is.

The corollary for the test suite, which cost a rewrite to learn: a source
dataset whose mountpoint is *inherited* puts nothing in the stream, so a test
built on one would pass with `-x mountpoint` removed and would be measuring
nothing. The pseudo-cluster's guests therefore carry local mountpoints, as
CBSD's do, and `tests/tier6/t_repl.sh` asserts that precondition before it
asserts the law.

## 6. Resume, observed end to end

A stream truncated mid-flight leaves the peer holding a token, and the partial
state is **not** a snapshot:

    cannot receive new filesystem stream: checksum mismatch or incomplete stream.
    Partially received snapshot is saved.
    A resuming stream can be generated on the sending system by running:
        zfs send -t 1-fe2c03fb3-e0-789c63606400...

    # zfs list -t all -r .../standby/alpha
    .../standby/alpha/web01    19.1M   -   19.1M   none      <- no snapshot

`zfs send -t <token> | zfs recv -s -u -x mountpoint -x canmount <ds>` then
completes it (rc 0), the token reads `-` afterwards, the snapshot appears, and
a later incremental works normally. All four steps observed, for a full send
and for an incremental one.

The reason this is a *requirement* and not an optimisation: a dataset holding a
token refuses every other stream.

    # zfs send -p -I @... | zfs recv -s -u -x mountpoint -x canmount <ds>
    cannot receive incremental stream: destination <ds> contains
    partially-complete state from "zfs receive -s".
    rc=1

So a tick that did not consume the token first would fail forever. That is the
mutation `tests/rediscovery/` exercises.

## 7. Foreign snapshots

Observed, on `zfs-2.4.2-1`: a snapshot created **on the replica** by something
that is not seance does **not** block a later incremental receive. A tick sends
straight through it, and the prune never names it, because the prune only names
snapshots that parse as seance's *and* carry the right node key.

    .../standby/alpha/src@seance-alpha-20260101T002000Z
    .../standby/alpha/src@zrepl-20200101T000000          <- planted on the replica
    .../standby/alpha/src@seance-alpha-20260101T003000Z  <- arrived afterwards

`zfs send -I` also carries the intermediate snapshots between base and new,
including foreign ones taken on the *source*, so a foreign name can reach a
replica by legitimate means. It is left alone at both ends either way.

## 8. What this design does not do, stated rather than discovered later

- **Datasets destroyed on the source are not destroyed on the replica.** That
  is the price of refusing `-F`, and it is the right way round: seance leaks
  disk rather than destroying data it did not create. An operator removes a
  stale replica by hand, and `status` will keep showing its lineage until they
  do.

- **A tick that dies part way leaves a guest's datasets at different
  snapshots.** Each dataset has its own lineage, so a send that fails on the
  root and succeeds on a child leaves the child ahead. Observed in
  `tests/tier6/t_interrupt.sh`. **Requirement for M2:** promotion must choose
  the newest snapshot common to ALL of a guest's replica datasets, not the
  root's newest. A mixed-time tree mounted as a guest is a crash-consistency
  violation that no amount of care in the engine can undo after the fact.

- **A guest that gains a dataset gets a full send of it**, once, on the next
  tick. There is no way to make an incremental of something the peer has never
  seen, and this is the honest cost of walking the tree.

- **A stream cut by the network cannot be resumed until the peer's half has
  ended.** Removing a node's port from the bridge drops packets; it does not
  tell the peer, and the peer's `zfs recv` goes on waiting on a TCP connection
  that has no way to know. Ticking again the moment the partition heals meets:

      cannot receive resume stream: destination <replica> contains
      partially-complete state from "zfs receive -s"

  — the ORPHANED receive still owns the dataset and the new one cannot take it
  over. Observed in `tests/tier6/t_replfail.sh`, which is why that stage ends
  the orphan explicitly rather than waiting on a retransmit timer. The tick
  reports the pair as failed and keeps the timestamp the peer was last known to
  hold, which is correct; the pair recovers by itself on the first tick after
  the peer's receive dies (a TCP timeout, or the reboot that usually comes with
  a real partition). **Nothing in seance kills a peer's process**, and nothing
  should: a receive that is still running may still be making progress, and a
  replication engine that reaps processes on a machine it does not own is a
  larger weapon than this one is allowed to be.

## 9. Where replicas live

    <standby_root>/<homenodekey>/<basename of the guest's dataset root>/<tail>

`standby_root` is a fleet key. The token `%n` in its value is replaced by the
node key of the node that **owns** that standby root — the peer (D-59). A fleet
whose nodes have identical pool layouts never meets `%n`:

    standby_root=<pool>/standby

A fleet whose nodes do not — different pool names, or a per-node subtree — uses
it, and still keeps ONE configuration file across the mesh, which is the
invariant `verify` enforces:

    standby_root=<pool>/state/seance/%n/standby

Unset means derive: the guest dataset root's parent, plus `/standby`, which for
CBSD is `<pool>/standby` because a CBSD guest's dataset is `<pool>/<jname>`
(D-6). A derivation can only speak for the node doing the deriving, so a fleet
whose layouts differ must set the key.

The standby parents — `<standby_root>` and `<standby_root>/<homekey>` — are
created `canmount=noauto mountpoint=none` and asserted on every tick. A repair
is logged at `warning`; `verify` reports the same properties read-only and
fails on them rather than fixing them.

## 10. Locks, cadence, and the crontab line

Each guest-peer pair runs under `lockf(1)` on
`<run-dir>/lock/<guest>.<peer>`, in a fresh invocation of the dispatcher
(`repl --locked`). `lockf` releases when the process dies, which a lock file
carrying a pid does not; and a pair that wedges takes only its own process with
it. A tick that finds a pair locked logs it and counts it as *in progress* —
the tick's own exit status is unaffected, and `status` shows the pair as
`in-progress` by asking for the lock and letting it go again.

`lockf -s -t 0` exits **75** (`EX_TEMPFAIL`) when it cannot take the lock;
observed.

The crontab line fires at the shortest cadence in the fleet, and each guest
decides for itself whether it is due, from its own lag records (D-61). One
entry, whatever the spread of per-guest cadences:

    */1 * * * * root /usr/local/bin/cbsd seance repl

The command is the PLATFORM'S verb, which `adapter_fact verb` answers with
(D-117), and not the dispatcher under `bin/`. cron(8) gives a job `PATH`,
`HOME`, `LOGNAME` and `SHELL` and nothing else, and the dispatcher learns which
node it is on only from what the module's verb wrapper exports (D-2) -- so a
line naming `bin/seance` exits 2 with "no config file" every time cron fires
it, for ever, while `verify` reports the line as correctly installed. Measured
in the guest at M5.

The comparison runs in BOTH directions (D-141, ruled on in D-152). A lag
record more than `skew_tolerance` in the FUTURE is a clock that moved, not a
tick that has just happened: the guest is due, with a warning naming the guest,
the record and the skew. Without it a node whose clock stepped backwards --
ntp after a long outage, a hypervisor restoring a paused guest, a BIOS clock
read wrong at boot -- replicates nothing until wall time catches up, and its
verdict line reads exactly like a healthy tick with the gate doing its job. A
record in the future by LESS than the tolerance stays not-due: that is ordinary
jitter between two machines, and the tolerance is the line seance already draws
between the two (`status` clamps a replica timestamped ahead of the clock the
same way, D-38).

`crontab(5)` on FreeBSD 15.1: *"Each line in system crontab ( /etc/crontab,
/etc/cron.d, /usr/local/etc/cron.d ) has five time and date fields, followed by
a valid user name ... followed by a command."* `cron(8)` FILES names
`/usr/local/etc/cron.d` as the *"Directory for third-party package provided
crontab files"*, which is what seance is, so that is where
`verify --render cron` tells you to put it; `verify` accepts either directory
(D-63).

## 11. The lag record

    <state-dir>/lag/<guest>.<peer>      "<replica_ts|-> <tick_epoch> <rc>"

`<replica_ts>` is the newest snapshot the two ends had in common when the tick
finished — the *acknowledged* state, measured from the peer's own listing
rather than assumed from a send that returned 0. `status` reads these files and
never the peers, which is what lets a survivor answer about a dead node without
asking it (design §5).

The file name parses from the right: peer keys are `[a-z0-9]+` and cannot
contain a dot, so a guest whose own name has one still resolves.

## 12. The configuration mirror (decision D-82)

One dataset per node carries what the guests' own datasets do not.

    <pool-of-jails-data>/seance-sys      mounted at <state-dir>/sys

CBSD keeps a jail's registerable configuration in `${jailsysdir}/<n>/`, a plain
directory on the workdir dataset — **outside** `<pool>/<jname>`, so nothing
replicates it. A VM's is inside its dataset by accident of layout:
`${jailsysdir}/<n>` is a symlink to `${workdir}/vm/<n>`
(`sudoexec/bcreate:599`, restored after a receive by `sudoexec/zfs-recv:66-69`).
Without the mirror a survivor holds a jail's data and has no way to register
it.

Every tick, before anything is snapshotted:

    for each guest this node replicates:
        repl_sys_travels <guest>        # is its config already inside its own
                                        #   dataset tree? (resolve the symlink,
                                        #   compare against the mountpoints)
        if not:  mirror ${jailsysdir}/<guest>/  ->  <state-dir>/sys/<guest>/

then `seance-sys` is snapshotted **with the tick's own name** and replicated
like a guest: same grammar, same heirs, same `-p` / `-x mountpoint -x canmount`,
landing at `<standby_root>/<home>/seance-sys`. It needs no special case on the
receiving side — the shadow-mount law hides it exactly like a replica, which is
the point of giving it no wire of its own.

**The mirror is `cp -a` plus a prune, not `rsync -a --delete`.** rsync is
present on a real CBSD node (it is a CBSD dependency) but not inside a shape-A
pseudo-cluster node, which nullfs-mounts only the base directories. Two
implementations of one mirror is a worse answer than one, and what is being
copied is a few kilobytes, locally: rsync's delta algorithm buys nothing here.
The prune runs first and deepest-first, so a file the source no longer has
cannot survive under a directory the copy is about to recreate.

**Promotion** mounts the replica mirror **read-only** at a scratch path,
copies `<guest>/` into the successor's `${jailsysdir}/<guest>/`, and puts the
mountpoint back — `zfs mount -o ro` is a property that lasts only as long as the
mount, so there is nothing to undo. It is skipped when the guest's own datasets
already carried the configuration. **Failback** runs the same code against the
interim's mirror, and says which of the two happened rather than doing either
silently.

`seance-sys` is not a guest: estate discovery walks past it, and `repl` refuses
to run on a node that has a guest by that name rather than quietly replicating
one into the other's place.
